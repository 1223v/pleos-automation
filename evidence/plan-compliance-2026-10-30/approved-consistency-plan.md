# Pleos 프로젝트 정합성·TDD·보안 개선 계획

## 1. 조사 결과와 목표

현재 구조는 **Kotlin core → Android UI·실행 서비스·차량 어댑터**, **Node 서버 → AI·외부 연결**, **공유 JSON 계약·검증 증거**로 나뉜다. 최신 승인 문서와 사용자가 이번에 선택한 정책을 기준으로 구현을 맞춘다.

이번에 실행한 검증 결과:

| 검사 | 결과 |
|---|---|
| Kotlin core 단위시험 | 23개 통과 |
| 서버 시험·TypeScript 검사 | 10개 통과·타입 오류 없음 |
| Android 앱 JVM 단위시험 | `NO-SOURCE` — 추가 필요 |
| Android lint | 오류 0개·경고 15개 |
| 문서 링크·JSON 검사 | 오류 0개 |
| npm 취약점 검사 | 알려진 패키지 취약점 0건 |

위 결과는 제품 완성이나 보안 무결성을 의미하지 않는다. 트리거·승인·복원·예산 처리에서 수정할 부분을 확인했다. 설치된 **Node 24.12.0은 보안 수정 전 버전**이며, 공식적으로 수정된 24.22.1을 프로젝트 기준으로 사용한다. [Node 보안 공지](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)

현재는 조사와 기존 시험만 수행했다. 코드 수정·새 시험 추가·문서 갱신은 아래 구현 단계에서 진행한다.

## 2. 확정한 동작

- **시트 승인:** 시트 포함 루틴은 어떤 동작도 실행하기 전에 좌석·축·방향·검증된 이동 제한을 한 번에 확인한다. 승인은 해당 실행에만 유효하며 다음 실행에는 다시 확인한다.
- **출근 내비:** 열선이 불필요하거나 사용 불가해도 허용된 내비는 독립 실행한다. 열선 실패를 숨기거나 이미 실행한 내비를 자동 원복하지 않는다.
- **타이머:** 절전 시간도 경과시간에 포함한다. 복귀 시 만료됐으면 즉시 종료·알림 처리하며, 기기를 깨우는 권한은 추가하지 않는다.
- **AI 예산:** 일·월 경계는 `Asia/Seoul`로 통일한다.
- 실제 AI 호출 차단, 시트 검증 전 잠금, 필수 기능과 release 검증 기준은 유지한다.

## 3. 구현 순서와 인터페이스 변경

### A. 보안 기준과 서버 방어

- 프로젝트 전용 Node 24.22.1을 공식 체크섬으로 검증하고 실행 기준·최소 버전을 갱신한다. 전역 Node 설치는 변경하지 않는다.
- 생성·수정 요청을 구분하는 엄격한 입력 계약을 적용한다. 잘못된 타입, 생성 요청의 불필요한 기준 그래프, 오래된 수정 버전은 공급자 호출 전에 거부한다.
- OpenAI 공식 API 원점을 명시해 미검증 환경변수에 의한 전송 대상 변경을 막는다. 호출 비활성화·자동 재시도 금지·응답 저장 설정을 시험으로 고정한다.
- 실제 산정 비용이 예약을 넘으면 확인된 비용을 보존하고, 영속적인 차단 상태로 후속 호출을 막는다. 재시작으로 차단이 풀리지 않게 한다.
- 신규 예산 행에는 정확한 예약 시각과 KST 기간을 기록한다. 시각이 없는 기존 UTC 행은 겹치는 KST 기간에 보수적으로 반영하며 자동으로 비용을 해제하지 않는다.
- Home Assistant의 `unavailable/unknown` 상태를 성공으로 처리하지 않는다. 요청 전에는 차단하고, 요청 후 확인 불가는 `UNKNOWN`으로 남긴다. 최종 JSON 응답은 앱과 동일한 256 KiB 제한을 적용한다.

### B. 트리거와 실행 의미

- 활성 루틴 집합과 트리거 기억을 동기화한다. 비활성화·정의 변경 후 재활성화 시 과거 이벤트를 실행하지 않는다.
- `CONDITION_ENTER`는 기본 조건과 필터의 결합 상태로 진입을 판단한다. 기어·속도 갱신 순서가 달라도 같은 결과를 내도록 한다.
- 탑승·시각 트리거는 필터 변화만으로 새로운 이벤트를 만들지 않는다.
- 후보 탐지와 실제 실행 시작 기록을 분리한다. 300초 cooldown은 실제 시작부터 계산하며, 충돌로 버린 후보를 나중에 재생하지 않는다.
- 전체 그래프의 구조 검증은 유지하고, 동적 capability 검사는 선택된 동작 직전에 수행한다. 실행하지 않는 열선 분기가 내비를 선행 차단하지 않게 한다.
- 일반 병렬 실행의 실패 시 형제 취소 정책은 유지한다. 출근 예제는 내비 실행 후 조건부 열선으로 구성하고 부분 결과를 표시한다.

### C. 시트 승인과 차량 안전 경계

- 실행 조정자가 하나의 `runId`를 발급하고 승인·명령·이력에 공통으로 사용한다.
- 승인을 `runId`, 규칙 revision·의미 해시, 시트 계획, 연결 세대에 연결한다. 거부·만료·취소·정의 변경·재연결 시 무효화한다.
- MOVE 직전에 최신 상태·권한·영역·위치 범위를 다시 검사한다.
- STOP은 일반 이동 gate와 분리하고, 이동 제한 감시가 UI 지연에 종속되지 않도록 한다.
- 늦은 ACK, 연결 교체, SDK 재연결 대기 명령 때문에 정지를 확정할 수 없으면 복구 기록과 `UNKNOWN`을 유지하고 새 MOVE를 차단한다.
- 주행 중 내비·미디어와 시트 이동은 각각 공식 지원·에뮬레이터 증거가 확보된 경로만 개방한다.

### D. 편집 복원·실행 이력·타이머

- 초안 복원 우선순위를 순수 로직으로 분리한다. 같은 Gleo 요청을 다시 열 때는 최신 작업 초안이 우선하며, 새 요청만 최초 한 번 반영한다. CONTROL 요청은 저장·재전송하지 않는다.
- 실행 시작의 규칙 snapshot과 명령 전송·ACK·상태 확인·종료를 지속적으로 저장한다. 강제종료 후에도 어느 단계까지 진행됐는지 남긴다.
- Room은 **버전 1→2 비파괴 migration**을 제공한다. 기존 루틴·초안·이력은 보존하고, 과거에 없는 정보는 추측해서 채우지 않는다.
- 시계와 대기 경계를 주입 가능하게 분리한다. Android에서는 `elapsedRealtime` 마감시각을 사용하고 최대 1초 간격으로 남은 시간을 재평가한다.
- 전체 실행 시간 초과와 사용자 취소를 이력에서 구분한다. 프로세스 재시작은 과거 실행을 재개하지 않는다.

## 4. 기능별 시험과 TDD 방식

기존 코드를 전면 재작성하지 않는다. 기존 동작에는 회귀시험을 보강하고, 결함 수정과 새 동작은 **실패 시험 확인 → 최소 수정 → 통과 → 정리** 순서로 진행한다. 사후에 추가한 시험을 과거 구현의 TDD 증거로 표현하지 않는다.

| 기능군 | 반드시 검증할 사례 |
|---|---|
| 조건·트리거 | 초기 참, UNKNOWN, 비활성 중 변화, 센서 갱신 순서, cooldown 경계, 동시 후보 |
| 그래프·편집·시뮬레이션 | 분기·반복·병렬·합류, 제한값, 충돌, 패치 원본 보존, Undo/Redo, 실제 IO 호출 0건 |
| 공조·조명·열선·시트 | 영역·단위·범위·권한, 요청과 관찰 구분, 승인 전 명령 0건, STOP 실패·늦은 응답·연결 단절 |
| 저장·Gleo·복구 | 최신 편집 보존, 새 요청과 기존 요청 구분, 원자적 저장, migration, 단계별 강제종료, 재전송 0건 |
| 타이머·음원·앱·내비 | 절전·시각 변경·취소, 포커스 상실, 자원 정리, 앱 삭제·비활성화, 열선 실패와 독립 내비 |
| AI·서버·외부 연결 | 기본 무호출, 인증·입력·크기·동시성 제한, 예산 초과·재시작·KST 경계, 상태 불명·오류 정제 |

JUnit 4, `node:test`, 기존 coroutines 테스트 도구를 사용한다. 앱에는 JVM 단위시험을 추가하고 Android·SDK 의존 경계를 분리한다. Room·Manifest·실제 UI·SDK 계약은 계측시험으로 보완한다.

보안 시험에는 exported Intent 입력, 승인 위조, 임의 URL·패키지, 응답 크기, 토큰·로그·백업·APK 노출을 포함한다. 의존성 경고는 공식 권고와 영향도를 확인해 분류하며 일괄 최신화하지 않는다.

## 5. 기록과 완료 기준

- 기존 미커밋 변경을 보존한다. 서버와 Android는 파일 소유권을 나누고, core·앱의 공통 인터페이스 변경은 순서대로 통합한다.
- [기존 TODO](C:/pleos-automation/13_IMPLEMENTATION_TODO.md)에 R01~R20의 구현·시험·증거·차단 상태를 연결한다. 현재 정책과 초기 설계 이력을 명확히 구분한다.
- 보안 보고서는 위험도, 발생 조건, 코드 위치, 재현 근거, 수정·재시험 결과를 기록한다. 확정 결함과 조건부 위험, 미검증 항목을 구별한다.
- 각 수정의 표적 시험 후 전체 core·앱 단위시험·서버 시험을 실행한다. 최종적으로 타입 검사, lint, debug·계측·release 빌드, 문서·diff 검사를 수행한다.
- 공식 AVD 시험과 실제 API 시험은 단위시험과 별도 기록한다. 시트 두 축 이동·STOP, 실제 AI 평가, 동일 release 전체 흐름 10회가 남으면 **제품 전체 완료로 표시하지 않는다**.
